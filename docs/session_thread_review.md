# 会话 / Thread / Span 深度审查

审查范围：当前 Skill、数据契约、存储与测试计划，以及实际飞书 Matter、详情、双表、成果 Registry、成果正文、Dashboard。结论基于实际读取，不是独立模型盲测。修正方案均为提案；本轮不重写工作线、不外发消息、不新增服务。

## 结论

保留 Session / Thread / Span 三分法，但当前实现更接近“人工解释后写成表格”，尚未达到可靠的会话连续性系统。应先解决来源顺序、归线依据、版本和投影一致性，再扩充跨人协作。

Session 记录对话在哪里发生；Thread 表示持续推进的工作目标；Span 表示在一个会话来源序列中，围绕该工作目标展开的一段连续讨论。Thread 不是标签，也不是某份文档；Span 不是一句用户话，也不是随意挑选的相关发言集合。多轮只是常见结果，不是必须凑够的数量。

此前已通过的部分：Skill格式、飞书写入/回读、局部关联存在性。此前 A/B/A 与成果映射的结论范围偏大，不能视作语义正确性或可重建性的证明。

## 发现（按优先级）

### R1 / P1：Span 的连续性与当前 A/B/A 样本冲突

规则规定 Span 连续，同时允许同轮分主题。实际 span-ecosystem-1 把三项任务中的第3项纳入末尾；随后 span-arch-8 才记录同一发言的第1、2项。展示顺序由主题聚合形成，不能称为严格会话时间线。若以用户段落顺序计，这里至少需要在第1、2项切回 A 后，再用新的 B Span 表示第3项；如果采用并行主题投影，就必须明确其允许交叠，不能再用“恰好三个不交叠连续 Span”验收。

U-update-skill 一轮同时含展示和可复制性，助手又逐项回答，使简单问答对也不足以唯一表达源顺序。完整正确数量需先定义分段单位，而不是先指定三段再填写材料。

后果：主题相关性被误当连续性；同一句可能重复计数；跨会话继续时源顺序不可信。
建议：先形成有序来源单元，每个单元有 role、source locator、消息序号和段落范围；Span 从这些单元派生。同源内容一个主归属，其他关系作关联，不重复复制原话。来源缺失时只能标部分顺序可知。

依据：externalization.md:5；详情页 revision 2 与当前可见三项任务原始顺序。

### R2 / P1：可读表和结构化状态不一致，存在悬空引用

Matter 当前 architecture.span_refs 引用 span-arch-3/4/5/6，但解析该页事件后不存在相应结构化 Span 对象；它们只在历史 Markdown 表里。span-deploy-3/4 同样曾在表格中出现，不能因为表格写过 ID 就认为工作图已登记。

后果：人能看表，接手 Agent 却无法按契约恢复这些记录；不同读取方式得到不同工作状态。
建议：维护一个规范对象集合，两表及详情是它的投影。所有引用先查实体存在；缺失标 unresolved，不能悄悄由阅读者重新发明对象。旧表修复用 migration/correction，保留原来源和替代关系。

依据：Matter revision 6 的JSON引用集合与实体集合差集。

### R3 / P1：版本号被记录，但历史内容并未具备可恢复保证

成果登记 collaboration-path.observed_version=2，而实际文档已 revision 3；当前详情/表格仍只反映早期版本。记录 last observed revision 2 本身合理，但缺少 last_checked_at 和明确“历史观测”语义，review_state=current 容易误导成同步最新。

另外 read_page 只有 page_ref/detail 参数，当前工具没有按 revision 回取正文的参数。仅写 @2 并不能保证下次还读得到版本2。修改 Span 的反向链接后，已有成果输入从 span@1 改成 span@2，也不等于生成时使用过 v2。

后果：出处可以点击，但未必能重现实际输入；版本引用可能把后来补的关联误写为当时生成依据。
建议：区分“生成时输入快照”与“后补关联校正”。保存生成时用到的最小摘要/明确决定版本，或可恢复的不可变内容引用；不是保存全部聊天。无历史内容获取能力时标 historical_retrieval=unavailable，不承诺精确重建。展示检查时间与观测版本；变更正文后登记同步待办。

依据：Artifact Registry revision 4；协作路径正文 revision 3；read_page 工具声明；externalization.md:22–26。

### R4 / P1：重复维护反向关系，只检查JSON并未保证用户视图一致

之前发现 span-arch-7 缺 collaboration-path 反向引用，已把 JSON 升为 record_version 2。当前详情页仍只列 artifact:skill-externalization，虽然旁边又放了协作路径链接。修复了图的一处，却没有一致刷新所有投影。

后果：用户查看详情、结构化记录和成果表得到不同答案。只检查两个字段相互包含，会遗漏页面上真正展示的内容。
建议：只把一处关联集合当事实来源，反向列表由它导出；在纯 Skill P0 可用单次快照统一生成多视图，无需图数据库。投影保存基于哪版对象生成。修复后同时检查数据引用和可读链接，不以字符串包含代替语义验证。

依据：详情页 revision 2、Matter 的 E-ext-core-backlink-fix、Registry E-ext-core-artifact-source-fix。

### R5 / P1：外化过程被误写成被外化内容的业务依赖

协作路径正文登记 depends_on D-externalization-ui（双表/详情的展示要求）。展示要求影响文档的呈现或制作过程，并不天然决定“未安装者能否协作”这一业务结论。类似地，包含“本轮已生成/验证这份成果”的执行摘要不应又作为该成果生成时的输入。

后果：用户改表格布局可能触发协作方案正文过时；成果通过引用自己的完成摘要造成逻辑循环。
建议：每项成果分清业务依据、输出格式约束、生成过程、运行证据。只有业务依据变化才默认触发业务内容 review；格式变更影响展示，执行证据在产出之后登记。关联不等于依赖，反向可达不等于因果正确。

依据：Registry 当前两条 depends_on；span-arch-8 助手摘要与正文输入引用。这里是语义设计问题，不是API故障。

### R6 / P2：Thread 的粒度和身份稳定性尚无足够判据

architecture 当前承载运行拓扑、授权体验、日志正文、外化建模等不同目标。标题从“Phase 1 架构”展示成“架构与体验”，语义范围扩张但没有明确演进边界。新建生态 Thread 有独立目标，合理；不代表其余主题都应继续塞进旧 Thread。

后果：主线越用越宽，相关上下文越取越多；或者为每份成果新建 Thread，失去连续性。
建议：Thread 用“持续问题/目标 + 作用范围 + 当前待解事项”识别；标题只是显示。可独立推进和验收时才考虑拆线，且保留来源关系。同一成果可以贡献多个 Thread；同一 Thread 可以产生多个成果。Thread完成后有新证据可重开，不因新会话复制。拆分/合并先保留候选映射再确认，不批量迁移不确定历史。

依据：Matter Thread 对象与历史双表。需用混淆案例验证，不应立即把所有旧线拆碎。

### R7 / P2：来源与双方答复证据仍是自述，无法稳定增量去重

U-next-test、U-three-tasks 等是人工语义标签，没有独立来源索引。没有平台消息ID并不是错误；但不能每次重建重新命名。exchanges 主要用用户来源标签承载双方摘要，没有独立助手消息或工具回单引用。多轮助手承诺、实际执行和失败可能被压在一个“答”里。

后果：无法判断是否漏记/重复，后来的总结可能覆盖原来的承诺；一份摘要变成唯一事实。
建议：从现在起给可见来源登记稳定会话内序号、角色、内容范围及最小核验摘录；不保存凭据。助手“建议/承诺/执行中/已验证结果”分别标状态与证据来源。历史不能可靠还原时标部分覆盖，不能补造精确轮数。Span 的 open/closed 与最后处理游标在模型中表达，避免每轮都新建或不停全量重写。

依据：externalization.md:7、16；当前详情 exchanges；data_contract.md:66。

### R8 / P1：回放和“完整快照”语义不足，冷启动恢复未成立

Registry 实际事件存在缺失 delta_id/entity_type/entity_id/source_refs，修正事件还缺 event_type/timestamp；payload 既有数组也有对象。契约定义了必需字段，但写入没有执行一致校验。Dashboard snapshot-ext-core-v2 标 complete=true，却仅含近期增量，旧状态说“沿用此前快照”而没有明确 base_snapshot_id 或跨页版本向量。

后果：新 Agent 需靠猜测合并旧记录；字段缺失或同名来源会导致错误覆盖；complete 不能用来判断恢复完成。
建议：轻量统一事件信封，定义按 entity_id/record_version 合并、重复/冲突/更正处理。快照选完整投影或明确基底增量之一，不能混用；记录所覆盖页面/事件游标和缺口。不需要本地daemon或复杂Router，先用规范化记录与回读检查即可。

依据：data_contract.md:31–35；Registry三次事件信封；Dashboard snapshot-ext-core-v2。

## 建议保留与澄清的模型

| 对象 | 负责回答 | 不应承担 |
|---|---|---|
| Session | 哪个宿主会话、哪些有序来源、覆盖到哪 | 不以主题定义会话，也不把生成的工作名冒充原生标题 |
| Thread | 正在持续解决什么、已决定什么、下一步是什么 | 不等同分类标签/文档/一次对话 |
| Span | 这次在该会话哪里连续推进该Thread，双方说了什么 | 不把不连续相关内容拼成“连续” |
| Decision | 哪项主张由谁在什么范围接受/撤回 | 不把礼貌认可、执行授权和全篇成果接受混为一谈 |
| Artifact | 产出了哪个版本、用了哪些输入、能否取回 | 不仅是一个指向最新版的URL |
| View | 当前可读展示、基于哪份状态 | 不成为第二个可独立变更的事实库 |

Thread是跨会话连续工作的单位；Span是其中一次出现的来源范围。日常阅读可以聚合展示同一Thread的多段，但必须保留底层分段。用户不必看到所有编号，却应能找到双方讨论依据。

## 轻量工作循环（建议，未改写Skill）

读取稳定来源游标与工作状态 → 登记新来源单元 → 判断继续/切换/待定 → 更新当前Span和Thread → 提取有证据的决定与结果 → 输出前固定最小输入上下文 → 生成并验证成果 → 写规范事件 → 生成两表/详情 → 核验引用、版本和显示 → 更新明确范围的快照。

回复尚未结束时Span可以open；一次工具调用只是执行证据，不自动另建Thread或Span。说“继续那个方案”且有多个合理候选时，提出一个最小澄清；“收到/谢谢”等无工作增量可记录覆盖但不制造业务对象。摘要出现遗漏时修正摘要版本，不自动覆盖旧成果的生成输入。

## 三项架构决定草案

ADR-R01（proposed）：保留连续Span，另用Thread视图聚合不连续片段。优点是来源可追溯；代价是一个主题多次出现会有多个Span。替代方案为非连续摘录集合，但应另命名并另定验收，不能混用定义。

ADR-R02（proposed）：一个规范状态生成所有视图；双向引用可为派生缓存。优点是减少漂移；代价是需要一次投影一致性检查。P0仍用飞书，不引入新状态服务。

ADR-R03（proposed）：成果“生成时输入”固定保存，后补关系单独记录。优点是能解释生成依据；代价是要保存最小上下文快照和版本可回取性。无历史版本工具时明确降级，不制造精确溯源承诺。

## 下一轮验收，先测逻辑再测渠道

1. 同一目标连续追问三轮：用户与助手都被覆盖，不要求机械凑轮数。
2. 同一消息三个小项按 A/B/A 排列，助手按 B/A 回答：逐角色保留真实顺序，Thread视图仍可聚合，不能倒置会话表。
3. “继续”指向两条相近工作线：允许待定，测试澄清负担，不只统计高置信度成功样本。
4. 用户只接受方案第2点：只改变该决定，其他候选及成果accepted版本不变。
5. 助手说已完成但工具失败：保留承诺与失败，不把完成写成事实。
6. 同样来源再次处理：不新建对象；纠正归线时只生成一次明确的更正。
7. 一个成果使用两条Thread：固定真实输入，不把后来的执行摘要当输入。
8. 成果页面更新、旧版本不可回取：报告准确的观测和缺口；原成果来源不被后补关系倒改。
9. 数据关联修正后：双表、详情和Registry一致；不存在悬空引用。
10. 从当前入口冷启动恢复：只用飞书中的明确快照/基底，不借用本会话记忆，重建同样状态。

这是一份待执行矩阵，本轮没有创建新任务或跨Agent盲测。可靠性检查可确定性验收；语义归线需保留人工允许的多个合理答案。统计覆盖、误归、过度拆分/合并、用户纠错负担和成果重建成功率；不要把“模型自己生成A/B/A又查数组等于A/B/A”当语义测试。
